# 瑶光控制台信息架构与客户运营工作流优化设计

**日期：** 2026-08-31

**状态：** 用户已授权按推荐方案直接设计并实施

**实施分支：** 当前 `main` 分支，不创建功能分支或 worktree

## 1. 背景与结论

当前控制台把面向运营人员的名单、客群定义、客户导入和技术 Audience 对象分散在多个页面中；数据分析各页签又分别决定标题、页签、工具栏和说明的位置；新 Customer 360 只把字段堆进页签，丢失了旧版 Notifuse 联系人详情中清晰的双栏结构和就地编辑能力。

本轮采用以下结论：

1. 数据分析成为左侧菜单第一项，所有分析页使用同一页面骨架。
2. 中文菜单统一为“客户管理”“客群划分”“营销自动化”“素材模板”；英文名称、权限资源、API 和既有路由语义不变。
3. `/lists` 是唯一面向运营人员的客群划分工作台；`/audiences` 只保留兼容跳转，不再展示 Audience 定义器。
4. 营销活动直接选择名单，发布时对名单成员生成不可变快照，不要求用户先把名单包装成 Audience。
5. 批量导入移到客户管理，并把所选名单作为 Import Job 的持久化配置；导入只增加名单关系，不覆盖既有名单状态或退订、退信、投诉记录。
6. Customer 360 恢复旧版 Notifuse 的“左侧客户资料、右侧关系和活动”双栏结构，并允许有权限的用户就地修改标准资料、标签和自定义属性。

## 2. 目标与非目标

### 2.1 目标

- 分析页的标题、说明、页签、工具栏和内容顺序完全一致。
- 消除“客群定义 → 引用名单 → 构建客群”这一运营侧重复步骤。
- 名单人数从当前名单关系实时读取，并可主动刷新。
- 导入文件可同时绑定一个或多个名单，任务重启后仍保留绑定关系。
- Customer 360 默认呈现业务可读信息，技术 ID 降级到次要区域。
- 所有写操作遵守 Workspace 权限、Customer 写入权威、幂等和名单抑制状态保护。

### 2.2 非目标

- 不删除 Audience 数据表或公开 Audience API；已有集成继续兼容。
- 不删除 `/audiences` URL，而是跳转到 `/lists`。
- 不恢复侧栏折叠菜单或新增二级侧栏。
- 不在本轮增加 Customer Identity、Consent 的写入界面；它们继续只读展示，避免在没有完整审计设计时修改敏感身份和同意记录。
- 不修改英文菜单名、权限资源名或 RPC 端点名。

## 3. 信息架构与中文菜单

左侧菜单按权限过滤后保持以下业务顺序：

1. 数据分析；
2. 客户管理；
3. 客群划分；
4. 营销活动；
5. 营销自动化；
6. 素材模板；
7. 投递中心；
8. 设置。

中文翻译映射：

| 英文消息键 | 中文菜单文案 |
|---|---|
| `Customers` | 客户管理 |
| `Audiences` | 客群划分 |
| `Automation Journeys` | 营销自动化 |
| `Content Center` | 素材模板 |
| `Data Analytics` | 数据分析 |

`WorkspaceLayout` 中“客群划分”直接链接 `/lists`；`/lists` 和旧 `/audiences` 均高亮同一个一级菜单。旧 `/audiences` 路由在进入页面前替换为 `/lists`，不保留中转页面和“进入名单管理”按钮。

## 4. 数据分析统一页面骨架

新增共享的数据分析页面骨架，所有七个页签严格使用以下可见顺序：

1. 页签对应的唯一主标题；
2. 一句面向运营人员的说明；
3. 与标题同一行的页面级操作；
4. 数据分析路由页签；
5. 只影响当前报表的筛选或维度工具栏；
6. 页面具体内容。

主标题直接使用“营销概览”“网站概览”“实时访客”“多维分析”“转化目标”“归因规则”“分析标注”。页面不再同时显示“数据分析”和当前页签的第二个标题，也不在内容组件内部重复相同标题。

页面级操作归属如下：

- 营销概览：时区和 7/14/30/90 天范围；
- 网站概览、转化目标：日期范围和对比范围留在页签后的报表工具栏；
- 多维分析：导出操作放在标题操作区，维度、最小会话数和过滤条件放在页签后；
- 实时访客：右侧显示实时状态和人数，不再显示“返回网站概览”的重复导航；
- 归因规则、分析标注：创建、测试等领域操作保留在内容区，但移除内容组件自身重复的标题。

共享骨架负责标题、说明、操作区、页签和响应式间距；业务页仍负责数据获取、权限门禁、筛选和内容渲染。

## 5. 客户管理与 Customer 360

### 5.1 客户管理页

客户管理页保留一个主标题和说明，下方使用“客户列表”“批量导入”两个页签。客户搜索、合并客户开关、分页和列表只存在于“客户列表”；持久化导入工作流只存在于“批量导入”。

### 5.2 Customer 360 双栏结构

抽屉桌面宽度为 1200px，最大不超过视口；窄屏改为上下布局。

左栏固定展示客户画像：

- 头像占位、业务显示名、脱敏主身份、状态和标签；
- 外部用户 ID、状态、语言和时区的就地编辑行；
- 已设置的自定义属性，可按原始类型编辑或删除；
- “新增属性”支持字符串、数字、布尔值和 JSON；
- 客户编号、内部 UUID、创建时间和更新时间收进“系统信息”折叠区。

右栏先展示名单与动态客群归属，再展示活动页签：

- 行为时间线；
- 营销自动化；
- 投递记录；
- 身份与同意。

不再保留把同一信息拆散的“概览 / 身份 / 客群”顶层页签。名单名称优先于名单 ID；身份始终使用后端返回的脱敏值。

### 5.3 资料写入语义

前端通过现有 `/api/customers.upsert` 写入，使用 Customer UUID locator 和每次保存唯一的幂等键：

- 标准画像字段使用 `profile.status/language/timezone` patch；
- 自定义属性新增和修改使用 `profile.attributes.merge`；
- 删除自定义属性使用 `profile.attributes.unset`；
- 标签提交完整、去重后的标签集合；
- 外部用户 ID 使用顶层 patch。

保存成功后失效 Customer 明细和列表缓存并重新读取；409 冲突、权限不足和校验错误必须展示可操作错误，不以静默回滚掩盖失败。只有 `customers.write` 权限可见编辑入口。

## 6. 客群划分与名单人数

`ListsPage` 成为“客群划分”下的唯一页面，内容包括：

- 名单名称、业务说明、公开/双重确认状态；
- 当前有效客户数、待确认、已退订、退信和投诉数量；
- 新增、编辑、删除、主动刷新和查看名单客户；
- 空状态下直接创建首个名单。

人数继续以 `/api/lists.stats` 为事实来源，页面聚焦时刷新、写操作完成后失效缓存，并以短轮询更新。页面不再包含 Audience 组合规则，不再显示“客群定义”或“批量导入”页签，也不再保留单个名单卡片里的旧联系人 CSV 导入入口。

## 7. 名单原生营销快照

Audience API 保持兼容，但新的控制台活动配置直接保存 `audience.list`。为避免回退到发送时实时扫描名单，Campaign Version 增加可选 `list_id` 来源：

- 一个版本必须且只能使用“版本化 Audience”或“名单”之一；
- Broadcast 发布时无论来源是哪一种，都创建 Campaign Run 和快照任务；
- Audience 来源从已完成 Audience Build 读取成员；
- 名单来源从 `customer_list_memberships` 读取当前 `active` 成员；
- 两种来源均按 Customer UUID 稳定分页，写入同一 `campaign_recipient_snapshots`；
- 快照完成后活动才进入投递，之后名单变化不影响已发布活动；
- 投递前仍重新检查当前身份、同意、退订、退信、投诉、黑名单和频控。

数据库迁移 `v52` 为 `campaign_versions` 增加 `list_id`，把 `audience_id` 和 `audience_version` 改为可空，并增加来源互斥约束。既有 Audience 版本原样保留。

## 8. 可绑定名单的持久化客户导入

上传前用户可选择零个、一个或多个名单。选择项通过重复 `list_id` 查询参数传给 `/api/imports.upload`，并持久化在 Import Job 的 `list_ids` 字段中；任务历史展示绑定的名单名称。

导入处理遵守以下规则：

- 每行 Customer Upsert 与名单绑定都由同一个幂等输入描述；
- 新字段 `list_memberships_add` 只增加缺失关系，不替换 Customer 的完整名单集合；
- 已存在的 `unsubscribed`、`bounced`、`complained` 或 `pending` 状态不得被导入重置为 `active`；
- 新增关系默认 `active`；
- Worker 重试对 Customer 和名单关系均幂等；
- 任一行无法写入时保留明确错误，不把部分失败统计为成功；
- Import Job 的行数守恒、后台续跑、取消和失败明细行为保持不变。

数据库迁移 `v52` 同时为 `import_jobs` 增加非空 `list_ids TEXT[] DEFAULT '{}'`。新安装的最终 schema 定义同步包含两个变化。

## 9. 权限、错误与兼容

- 菜单和页面读取继续使用现有权限资源。
- 客户导入需要 `customers.write`；名单选择项只在有 `lists.read/write` 时展示。
- Customer 360 读取需要 `customers.read/write`，编辑需要 `customers.write`。
- 名单管理写操作继续需要 `lists.write`。
- 旧 Audience API、已有 Audience 数据和已有以 Audience 为来源的活动继续工作。
- 旧 `/audiences` 深链接采用 replace 跳转到 `/lists`，浏览器后退不会反复落入中转页。
- 新增后端错误沿用结构化 API 错误和 Request ID。

## 10. 测试与验收

### 10.1 前端

1. 导航测试固定数据分析为第一个可见菜单，并验证 `/lists`、`/audiences` 的选中关系和中文菜单文案。
2. 路由测试证明 `/audiences` replace 跳转 `/lists`。
3. 数据分析七个路由均只出现一个主标题，且顺序为标题说明、页签、工具栏、内容。
4. Customer 360 测试覆盖双栏信息、脱敏身份、标准字段修改、属性新增/修改/删除、标签保存、无写权限禁用和缓存刷新。
5. 客户管理测试覆盖客户列表与批量导入两个页签、多名单选择和上传参数。
6. 名单页测试覆盖实时人数、主动刷新、创建入口和不存在 Audience/Import 页签。
7. Broadcast 表单测试覆盖直接选择名单并提交 `audience.list`。

### 10.2 后端

1. `v52` 在既有 workspace schema 上幂等迁移，并正确注册为当前版本。
2. Campaign Version 校验覆盖 Audience、List、双来源和无来源。
3. 名单快照仅读取 active Customer，按 UUID 分页并生成不可变收件人。
4. Audience 快照的既有测试保持通过。
5. Import Job 的创建、读取、列表和重启处理均保留 `list_ids`。
6. `list_memberships_add` 只增加缺失名单，不覆盖已有抑制状态，也不删除未选择名单。
7. 导入行在重试后不重复创建 Customer 或名单关系。
